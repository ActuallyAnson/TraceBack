# Why the true service had origin share 0.0 on real telemetry (diagnosis, 2026-10-20)

Diagnosis only. No analyzer rule, prompt, converter or reported number was changed; no batch was re-scored. Scripts: `origin_trace.py` (replica of `correlate()` + analyzer v3's error-flag step + v2's origin share; it reproduces the analyzer's numbers for m10: 8644 traces, 11 failed entry requests, frontend 1.0) and `relink_whatif.py` (one incident, in memory). Raw OTLP for batch 3 was still on disk; batches 1 and 2 raw files are not.

## Two causes, both on the path from raw telemetry to the origin measure
**(a) Converter bug: parent links are lost when an intermediate span is dropped.** The converter keeps only server and client spans and drops internal ones (`kind 1`). In the raw m10 data the failing chain is
`frontend-proxy → frontend POST /api/checkout (server) → [frontend "executing api route", INTERNAL, dropped] → frontend client PlaceOrder → checkout → payment`.
When the internal span is dropped, the converter omits `parent_span_id` of the client span (its parent is not retained), and the per-entry-request re-keying then gives that subtree its own trace id. Evidence (m10): span ids are never rewritten or lost (0 of 27,092 converted ids missing in raw, 0 parents rewritten), but 2,602 `frontend` client spans, 252 `recommendation` client spans and 135 `checkout` client spans lost their parent because it was an internal span, plus 1,600 `frontend-proxy` and 73 `flagd` server spans whose parent was a dropped client/server span from a dropped service. 5,646 of 8,644 traces have a root server span; the other ~3,000 are detached subtrees. All 11 failing payment server spans sit in such a detached trace (top ancestor: `frontend` client PlaceOrder, "no root server span"); 0 of them are in a trace counted as a failed entry request. So: numerator for payment 0, denominator 11 (the failed entry requests are the 11 `frontend-proxy` roots whose subtree stops at the frontend).
**(b) Definition problem: a masking 4xx span breaks the failure walk even once the link is restored.** With the 2,985 orphans re-parented to their nearest retained ancestor (what-if, m10 only, in memory), all 11 payment failures are inside the 11 failed entry traces, yet the origin share is still frontend 1.0, payment 0.0: the tree is `proxy server 500 → proxy client 500 → frontend server 422 → frontend server 422 → frontend client PlaceOrder 500 → checkout 500 → payment 500`. The origin walk follows only failing children, and the two frontend 422 spans (no error flag) are not failing, so the walk ends at the proxy client. Analyzer v3's S2 promotes a 4xx span only if it has an error flag or is the *direct parent of a span S2 itself promoted*; here the child is natively 500, so nothing is promoted.

## The other runs where the true service was among the model's proposals
- **m12** (product-catalog): same cause (a). 85 failing product-catalog spans, none in a failed entry trace; top ancestors are detached `frontend`/`recommendation`/`checkout` client spans with no root server span. 51 failed entry requests, 50 attributed to frontend.
- **m03** (cart): same detachment. The 10 failing `checkout → cart` client spans (500, error flag) hang under a detached `frontend` client PlaceOrder span. m03 also has 0 failed entry requests, so even the denominator is empty; whether (b) applies there was not tested.
- **m11** (paymentUnreachable): payment has no server spans (it is unreachable). The 23 failing `checkout` client spans (503, error flag) hang under a detached `frontend` client PlaceOrder span (cause a), and they carry no `peer` (the bad address names no instrumented service), so even with links restored the origin would be `checkout`, not `payment`. Under the edge scoring either endpoint counts as correct, but this was not tested.
- Same cause, same data path, so (a) explains all four; (b) was confirmed on m10 only.

## Could the simulator results be affected?
Not the same way. The simulator never drops a span class: it loses 4% of spans at random, and 4.0% of traces with a failing span have no root server span, against 29.9% in the four real runs inspected (35.4% of all their traces). Its 4xx spans are 4,004 of 3.1 million. The analyzer was developed with that random loss (it re-attaches lost *server* parents by containment). The real loss is systematic: it removes exactly the intermediate span that connects the entry request to the subtree where the fault is, and the orphan is a client span, which the containment rule does not re-attach. I did not run a simulator re-score; the simulator results are unchanged.

## What this means for the real-telemetry numbers
Plainly: the analyzer, Full Traceback and hybrid numbers on real telemetry (1/7, 0/10, 1/10, 0/10 and the hybrid's) partly reflect a conversion error (a), plus an analyzer rule that is too narrow for how the demo reports failures (b). They are therefore not evidence about the approach on real traces as such. The baseline reads logs grouped by (re-keyed) trace ids, so it is affected less directly. Nothing was re-run.

## Proposed fix (not applied) and expected scope
1. **Converter (new version, e.g. v3; v2 and its hashes stay frozen):** when a retained span's parent was dropped, walk up the raw parents to the nearest retained ancestor and use it as `parent_span_id`, before re-keying. Scope: converter only; ~2,985 of 27,092 spans in m10 change their parent, the number of traces falls from 8,644 to 5,659, nothing else changes.
2. **Analyzer (new version, e.g. v4):** make the S2 rule "a 4xx server span with a failing descendant counts as failed" (instead of "direct parent of a span S2 promoted"). Scope: only 4xx spans, which are rare in simulator data (4,004 of 3.1 M spans), so a v3-equals-v4 check on the simulator sets is cheap and should be run first.
3. Optionally carry a client span's unresolved target as an unknown peer rather than none (m11).
4. Verification must use a **fresh, locked batch 4** (the raw files of batches 1 to 3 cannot be reused as a test: they were examined here), plus the existing hash checks and a simulator no-change check.
